# Сопровождение проекта

## Перед изменением

Прочитать [README](README.md) и нужный раздел [документации](docs/README.md), затем проверить `git status`. Рабочая версия сейчас находится в `codex/dinov2-recognition`; новые ветки обычно именуются `codex/<описание>`.

Не смешивать пользовательские локальные материалы, фотобазу и изменения исходников. Каталоги `.agents/`, локальные исследовательские материалы и папка ручных фото могут существовать вне текущего изменения. Добавлять в коммит только явно проверенные файлы.

## Согласованность данных

- Источник соответствия ONNX-индексов — `config/model_labels.json`; сохранять исходный порядок всех 38 выходов.
- Включённый класс должен иметь согласованные `conditionId`, `cropId`, карточку, фотографии и метаданные культуры.
- Изменения справочника не дообучают модель. Поддержку новых заболеваний подтверждать реальной моделью и измерениями.
- Не удалять legacy-карточки только ради очистки видимого справочника: старые записи журнала используют их ID. Видимую область задаёт `catalog.ts`.
- Новые фото сопровождать происхождением, атрибуцией и лицензией. `hasRealPhotos` не является признаком проверенных прав.
- Изменение seed не обновляет существующие SQL-записи автоматически; документировать миграцию/обновление отдельно.

## Проверки по типу изменения

| Изменение | Минимально подходящие проверки |
|---|---|
| Только документация | Факты/команды по исходникам, существование ссылок, `git diff --check` |
| Карточки/реестр/фото | `npm test`, model-package tests; согласованность Python seed; UI при изменении видимости |
| Политика, preprocess, Worker client | Unit, настоящий Canvas/WASM smoke, E2E распознавания и отказа, TypeScript, build |
| UI или журнал | Соответствующие E2E, unit журнала при изменении хранения, TypeScript, build, узкий и широкий viewport |
| Python/БД/импорт | `python -m pytest`, проверка CLI на временной БД; миграция при изменении схемы |
| Модель/пороги | Полный набор затронутых тестов и отдельные измерения качества/времени с версией и manifest |

Полные команды: [testing.md](docs/testing.md). Не выдавать историческое прохождение тестов за свежий результат текущего коммита. Для документационных правок не требуется повторный долгий benchmark, который перезаписывает отчёты.

## Работа с ресурсами

`.gitattributes` отключает преобразование строк у закреплённых модельных артефактов и JSON-отчётов benchmark. Это нужно для совпадения SHA-256 на Windows. Не пересохранять эти файлы редактором ради форматирования.

`npm run prepare:model` при повреждённом файле останавливается; восстановить корректный артефакт, а не переписывать эталонный хэш. Замена модели должна иметь новую ревизию, согласованный Worker и обновлённые тесты.

`npm run evaluate:model` пишет в исторические пути отчётов. Перед публикацией сохранить новый запуск отдельно с датой и версиями. Эталонный ответ используется только для оценки, не передаётся движку распознавания.

## Документация рядом с изменением

- Меняется команда запуска/зависимость → обновить основной и соответствующий README.
- Меняется набор состояний → `docs/recognition.md`, таблицы README, coverage и тесты.
- Меняется хранение → `docs/architecture.md`, `docs/data-and-licenses.md`, описание миграции журнала/SQL.
- Меняется Vercel, ветка или домен → `docs/deployment.md` и ссылку приложения в README.
- Меняется результат измерений → отчёт с методом, manifest, версиями, условиями и ограничениями.

Исторические планы не переписываются под новый UI; для актуальных инструкций служат руководства. Новую лицензию на весь код нельзя выводить из лицензии отдельной зависимости: это отдельное решение владельца проекта.

## Git и публикация

Перед commit просмотреть staged diff, исключить секреты/локальные базы/пользовательские фотографии. Писать сообщение по итоговому изменению, например `docs: add project setup and architecture guides`.

Push в рабочую ветку может запускать Vercel Preview. Успешный push, успешный build и работающее приложение — отдельные факты; при публикации указывать, что именно проверено. Не выполнять force-push или переключение production в рамках обычного обновления документации.
