## Зачем нужен доступ к файлам вне frontend

Frontend импортирует `../config/model_labels.json` и `../config/model_conditions.json` через исходники. В `next.config.mjs` включён `experimental.externalDir`, а в Vercel необходимо разрешить включение файлов вне корневой папки сборки. Перенос только `frontend/` без общих JSON сломает сборку.

Рабочая конфигурация находится в [frontend/vercel.json](../frontend/vercel.json). Корневой [vercel.json](../vercel.json) содержит альтернативные команды установки/сборки от корня репозитория. Для существующего проекта использовать настройки с Root Directory `frontend`, не смешивать оба режима.

## Обновление через Git

Перед отправкой выполнить проверки, подходящие изменению: [testing.md](testing.md). Из корня:

```powershell
git switch codex/dinov2-recognition
git status --short
# Добавить только проверенные файлы конкретного изменения.
git add README.md docs/README.md
git commit -m "docs: update project documentation"
git push origin codex/dinov2-recognition
```

Список `git add` выше — пример, не полный набор файлов любого обновления. Не использовать без проверки `git add .`: локальные фото, пользовательские материалы и файлы окружения могут не относиться к изменению.

Git-интеграция Vercel создаёт Preview после push. В dashboard проекта открыть Deployments и проверить commit, ветку, статус Ready и назначение нужного домена. Наличие commit в GitHub само по себе не означает, что Vercel завершил сборку.

Для документационных коммитов приложение по умолчанию также может пересобираться: отдельного правила пропуска таких сборок в репозитории нет.

## Домены

Путь настройки: Vercel → проект `frontend` → Domains. У `agro-pomoshchnik.vercel.app` задано подключение к Preview и конкретной ветке. Оно сохраняет адрес при следующем успешном деплое этой ветки.

При переходе на другую release-ветку доменную привязку нужно обновить отдельно. Не переназначать её случайно на старую Production-сборку. Для собственного платного домена потребуются отдельно регистрация и DNS; текущий поддомен `vercel.app` этого не требует.

Журнал хранится на стороне браузера и привязан к домену. На новом адресе он будет отдельным, даже если версия приложения та же. Автоматического переноса истории между preview-адресами нет.

## Проверка после сборки

1. Убедиться в Ready и правильном commit/ветке в Vercel.
2. Открыть читаемый адрес: должны быть загрузка/камера без выбора культуры, coverage на пять культур и 21 состояние.
3. Выполнить анализ известного снимка; проверить загрузку Worker, ONNX и WASM без 404.
4. Проверить справочник на пять культур и 24 состояния, открыть журнал и обновить страницу.
5. Проверить console/network; фотография пользователя не должна уходить API распознавания.

## Ошибки деплоя

| Ошибка | Что проверить |
|---|---|
| Не найден Next.js / `onnxruntime-web/dist` | Root Directory и выполнение `npm ci` внутри `frontend` |
| Не найден общий JSON | Include files outside root и `externalDir` |
| Ошибка контрольной суммы модели | Совпадение артефактов с закреплённым manifest, настройки `.gitattributes` |
| Модель скачивается/собирается долго | Build logs, сетевой доступ к источнику; не считать сборку зависшей только по паузе между строками |
| Новый commit есть, сайт старый | Статус сборки, ветка домена, назначенный deployment |
| Домена нет на выбранном деплое | Проверить branch-specific назначение в Domains и нужное Preview environment |

Пользовательские секреты не требуются для inference. Не помещать Vercel/GitHub токены в `NEXT_PUBLIC_*`, source, screenshots логинов или коммиты. Авторизация для dashboard/CLI настраивается отдельно от runtime сайта.

## Возврат к предыдущей версии

Выбрать в Vercel известную успешную сборку нужной ветки и проверить её отдельно. Временное переназначение домена и откат кода через Git — разные операции. Для обычного исправления рабочей Preview-ветки предпочтителен проверенный исправляющий/revert-коммит с новым успешным деплоем. Не выполнять production rollback/promote для исправления одной preview-ссылки без отдельного решения о production.
