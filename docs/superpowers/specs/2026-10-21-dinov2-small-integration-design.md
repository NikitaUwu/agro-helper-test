## 2. Проверенная модель и её границы

Первичные источники:

- [Карточка модели](https://huggingface.co/rodynaemad/plant-disease-dinov2-small).
- [Классы и архитектура](https://huggingface.co/rodynaemad/plant-disease-dinov2-small/blob/main/config.json).
- [Параметры обработки изображения](https://huggingface.co/rodynaemad/plant-disease-dinov2-small/blob/main/preprocessor_config.json).
- [Эталонный браузерный код автора](https://huggingface.co/spaces/rodynaemad/plant-disease-scanner/blob/main/index.html).
- [Параметры OOD](https://huggingface.co/spaces/rodynaemad/plant-disease-scanner/blob/main/meta.json) и [файлы Space](https://huggingface.co/spaces/rodynaemad/plant-disease-scanner/tree/main).
- [Лицензия Space](https://huggingface.co/spaces/rodynaemad/plant-disease-scanner/blob/main/README.md).

Ревизия модели, видимая при проверке: `06ebf5e308e100fd000d738c42b059ebb5f58a16`.
Ревизия Space с эталонным кодом/centroids/meta: `b26e704bd72c2fe05632ea6f7be680a2eca0d8f5`.

Из карточки: классификатор выдаёт 38 классов для 14 культур. ONNX INT8 занимает примерно 24 МБ, FP32 — около 88 МБ. Вход `pixel_values` — float32 `[1,3,224,224]`; выходы — `logits` и 768 признаков `features`. Это классификация одного листа, без сегментации, определения площади поражения и оценки тяжести болезни. Заявленные автором 98.9% относятся к PlantVillage; полевое качество для нашего продукта не измерено. Модель всегда выбирает известный класс, даже если изображение не подходит.

Важные детали, проверенные по конфигам и исходнику:

1. RGB; короткая сторона → 256; центральный crop 224×224; деление на 255; mean `[0.485,0.456,0.406]`, std `[0.229,0.224,0.225]`; CHW float32. `image_size: 518` в архитектурном config не является размером входа опубликованного ONNX.
2. В image processor указан bicubic (`resample: 3`). Browser-пример использует Canvas с высоким качеством интерполяции и округлением размеров. Нельзя обещать попиксельную идентичность Canvas и PIL: это отдельно проверяется на одинаковых изображениях.
3. OOD — отдельная процедура, а не часть `logits`: максимум косинусного сходства features со всеми 38 нормированными центроидами. В Space есть `centroids.f32`, 38×768 float32, и `meta.json` с `dim=768`, `threshold=0.699429452419281`.
4. Исходный browser-пример использует `onnxruntime-web@1.30.0`, WASM. Для пилота фиксируем эту проверяемую отправную версию и затем её lockfile; не используем `latest`.
5. OOD помогает отсеивать явно посторонние снимки. Он не гарантирует отказ на огурце, неизвестной болезни, дефиците питания или смешанном поражении.
6. `healthy` трактуем как отсутствие характерных видимых признаков известных состояний на листе. Это не подтверждение здоровья всего растения или отсутствия патогенов.

Весов в рамках планирования не скачивали; inference и мобильная производительность этой модели ещё не проверены.

### Что сознательно пока не добавляем

| Культура модели | Причина |
|---|---|
| Голубика, малина, соя | У каждой есть только healthy. Нельзя предлагать диагностику заболеваний с таким покрытием |
| Апельсин | Есть только Huanglongbing, нет healthy и альтернативных причин симптомов |
| Squash | Есть только мучнистая роса, нет healthy; это не огурец и не универсальная категория «все тыквенные» |

Эти 5 выходов остаются в вычислении всех 38 вероятностей и OOD. Если такой класс занимает первое место, показываем ограничение поддержки; не подставляем следующий разрешённый класс.

Одинаковое английское название болезни разных культур не означает один выход модели. Cedar apple rust нельзя обобщать на все виды ржавчины яблони; bell pepper — на любые перцы; Orange — на все цитрусовые. Русские названия и рекомендации новых карточек сверить с профильными первичными источниками до включения.

## 5. Архитектура и альтернативы

**Рекомендуемый вариант: ONNX INT8 в браузере, WASM в Web Worker.** Фото остаётся на устройстве, платный внешний API не нужен, текущая схема Vercel сохраняется. Ограничения: начальная загрузка весов и WASM, память и скорость телефона. Доступность и время ответа проверяем до включения функции. Файл 24 МБ не означает 24 МБ потребления RAM.

Альтернатива 1: отдельный CPU inference-сервис с тем же контрактом результата. Убирает тяжёлое вычисление с телефона, но требует хостинга, загрузки фотографий и обслуживания. Рассматривать отдельным следующим решением только если browser-spike не проходит; скрытую отправку фото не вводить.

Альтернатива 2: Python/PyTorch. Подходит для сравнения и офлайн-оценки, добавляет более тяжёлые зависимости и не является прямым продолжением текущего frontend. Для пользовательского MVP пока не выбираем.

Поток: файл / существующий образец → проверка и декодирование → фиксированная предобработка → Worker/ONNX → softmax всех 38 классов + OOD → политика принятия → существующая карточка результата → локальный журнал.

Модельный пакет доставляется с нашего origin по пути с ревизией. Во время реализации скачать только зафиксированные ONNX/config/preprocessor/meta/centroids, сохранить SHA-256, размеры, ссылки и лицензии в manifest. Веса и Runtime/WASM не попадают в начальный JS bundle; загружаются при первой попытке анализа. Не загружать PyTorch-веса в клиент. Не ходить на HF `main` при каждом пользовательском запросе.

Начальный кандидат Runtime — `1.30.0`; WASM/JS должны быть из одной версии. Применяем `numThreads=1` для работы без обязательных COOP/COEP. WebGPU и многопоточность — вне первого внедрения. Браузерный cache по ревизии допускается через Cache Storage; при отказе хранилища работает сетевая загрузка без кэширования. Полную офлайн-доступность приложения без service worker не обещаем.

Разделение ответственности: `config/model_labels.json` — соответствие классов для Python и frontend; `frontend/src/lib/diagnosis/` — файлы обработки, принятия решения, клиента и Worker; React-компоненты только показывают состояние. Для frontend JSON вне каталога root импортируется с явной настройкой `experimental.externalDir` в Next.js и включением пути в TS; проверить production build. Без этой настройки нельзя считать общий реестр уже доступным сборке.

## 6. Контракт результата и безопасный отказ

`DiagnosisRequest`: `requestId`, `image: Blob`, `selectedCropId: CropId`, `source: 'upload' | 'sample'`.

`DiagnosisOutcome` — discriminated union:

- `status: 'accepted'`: `conditionId`, `cropId`, `score` в [0,1], `top3`, `oodSimilarity`, `modelRevision`, `preprocessingVersion`, `policyVersion`, `source`, `inferenceMs`.
- `status: 'uncertain'`: `reason: 'low_score' | 'ambiguous' | 'ood' | 'crop_mismatch' | 'unsupported_class'`, исходные top3 и модельные метаданные; без назначенной болезни и риска.
- `status: 'error'`: `reason: 'invalid_file' | 'decode_failed' | 'model_load_failed' | 'inference_failed' | 'timeout'`, русское сообщение с действием повторения.
- `status: 'cancelled'`: только requestId; без карточки болезни и записи журнала.

Каждый исход несёт requestId. Все численные выходы проверяем на форму, конечность и допустимые диапазоны. Поток отмены прерывает fetch; начавшееся вычисление отменяем завершением Worker либо игнорируем по requestId, не позволяя позднему ответу сохраниться в журнал.

Порядок политики: проверка чисел/формы → OOD → глобальный top1 → разрешённость класса → совпадение выбранной культуры → score и разница top1/top2 → accepted. Softmax и top-k всегда по всем 38 классам. Запрещено фильтровать классы перед softmax, перенормировать оставшиеся или заменять неподдерживаемый top1 следующим классом.

До калибровки только внутренний эксперимент: `max score ≥ 0.85`, `top1-top2 ≥ 0.20`, cosine ≥ `0.699429452419281`. Это инженерные стартовые пороги, не подтверждённые вероятности правильного диагноза. Для публичного пилота их заменяет зафиксированная политика, выбранная на отдельной calibration-выборке и проверенная на test. Не прошедшие классы можно оставить catalog-only.

Системный риск из справочника — характеристика состояния, а не измеренная степень поражения на фото. Не отображать его для uncertain/error как установленный факт. Top3 доступен через компактное раскрытие и подписан «Возможные варианты».

## 8. Совместимость, хранение и Python

1. Существующие class/crop ID и 25 карточек сохраняются. На этапе A добавляются 5 карточек томата, на B — 16 карточек 6 новых культур. `diseaseCount` и заголовки считаются программно; healthy отдельно от болезней.
2. Вводим `analysisAvailability` на карточке/культуре. Неподдерживаемое моделью состояние остаётся доступно поиску и старым записям.
3. Ключ localStorage v1 сохраняется для обратной совместимости. Loader принимает старую запись и новую запись с `schemaVersion: 2`; у старой `origin='legacy_demo'`, её фиктивная confidence не показывается как score модели. Старое значение при чтении не перезаписываем.
4. В новых записях accepted автоматически сохраняем только thumbnail: длинная сторона до 640 px, JPEG до 80 КиБ, без EXIF/GPS. Blob URL для текущего полного фото живёт только до закрытия результата. QuotaExceeded → результат остаётся доступен, явно «Не удалось сохранить в журнал», отметка «В журнале» не появляется.
5. Для новых записей — origin, modelRevision, policyVersion, preprocessingVersion, status и score. Каталожная закладка имеет origin=catalog и score=null. Отмена, runtime error и uncertain автоматически не записываются как диагноз.
6. В Python расширяем `SEED_CLASSES`, ingest-map и downloader теми же ID через общий реестр. Старые таблицы и записи не удаляем; для добавления классов достаточно идемпотентного seed, миграция SQL-схемы не нужна.
7. `config/taxonomy_seed.json` остаётся отдельной таксономией со старыми UUID: новые hosts/pathogens/conditions/target_classes добавляем с новыми стабильными UUID, не подменяем действующие. Сверяем пересечение slug с реестром.
8. `ModelEvaluation` сейчас недостаточен для полного отчёта с abstention, top-k и OOD. Для первого внедрения пишем versioned JSON/CSV в `data/evaluations/`, краткий отчёт — в `docs/evaluations/`; не расширяем SQL-схему только ради browser-MVP. Учитывать отдельно статус accepted и отказ, не считать отказ обычным неправильным disease ID.

## 9. Проверка качества и условия включения

Три разные проверки:

- **Интеграционная:** существующие 60 PlantVillage-снимков плюс примеры автора. Проверяет вычисление и mapping, не независимую accuracy: они могут пересекаться с обучающими данными.
- **Калибровка:** независимые разрешённые снимки со сложным фоном и экспертно подтверждённым классом; отдельные группы листьев/источников, не совпадающие с test. На ней выбираем пороги.
- **Тест:** зафиксированные до настройки снимки, без повторной подгонки порогов. Для этапа A планировать минимум 20 снимков на каждый из 17 классов, плюс ≥100 неподдерживаемых примеров. Calibration собирать отдельно. Это нижняя граница пилотной проверки, а не основание рекламировать точность с узким доверительным интервалом.

Неподдерживаемые примеры включают огурец, пшеницу, мучнистую росу яблони, паршу/ризоктониоз на клубнях, healthy-only культуры, неизвестные болезни известных культур, дефицит питания, смешанные симптомы, не-листья и непригодные фото. Для публичного бенчмарка нужны открытые источники с подтверждённым коммерческим разрешением; при нехватке таких данных остаёмся во внутреннем эксперименте, не заменяем полевой test PlantVillage-образцами. Фотографии пользователей автоматически в датасет не собираем.

Предложенные ворота небольшого публичного пилота (считаются на test, не на calibration):

- Доля верных среди accepted ≥90% отдельно для каждой включённой культуры; принятие ≥50% её подходящих тестовых фото, чтобы исключить «решение» отказом на всём.
- Для accepted healthy — precision ≥95%; дополнительно отчёт о больных листьях, ошибочно признанных healthy, и размере выборки.
- Ложное уверенное принятие на ≥100 неподдерживаемых test-снимках ≤5%; отдельно показать результаты именно на огурце/пшенице и неизвестных состояниях, а не только на не-листьях.
- Отдельно посчитать по классам, показать confusion matrix, количество отказов, coverage, top1/top3, исходные числа и 95% доверительные интервалы. При слишком малом числе accepted вывод «данных недостаточно».
- По скорости: целевой p95 повторного анализа ≤5 секунд на выбранном среднем Android и iPhone, измерить не менее 30 запусков на устройство. Это цель spike, не текущее обещание. Отдельно измерить cold download/init и пиковую память; не маскировать ожидание искусственными двумя секундами.
- Работа каталога/журнала не зависит от загрузки модели; анализ не блокирует UI. Провал браузерной совместимости или качества — основание оставить режим экспериментальным/недоступным, а не вернуть mock.

Матрица: Android Chrome, iPhone Safari, desktop Chrome/Edge; без WebGPU; сеть медленная/оборвана; пустой cache; отказ Cache Storage; отмена; повторная съёмка; исчерпание localStorage. Набор браузеров и конкретные устройства записать в отчёт.

## 11. Границы работ и порядок

Только планирование выполнено сейчас. Следующая реализация: технический spike → реестр и этап A → настоящий scanner → результат и журнал → проверка/включение → этап B.

Не включаем в этот объём обучение/дообучение, аккаунты, облачный журнал, пользовательские фотоархивы, сегментацию, автоматическую агрономическую оценку тяжести, глобальный редизайн, обязательный GPU и переписывание Python-пайплайна.

Оценка порядка величины для одного разработчика: spike 1–2 рабочих дня, этап A ещё 4–6 дней, контент/интерфейс/проверка этапа B ещё 3–5 дней. Итого примерно 8–13 рабочих дней инженерной работы; получение независимых разрешённых полевых фото и агрономическая проверка могут занять дополнительное календарное время. Это оценка, не гарантированный срок релиза.
